# money.log v2 — план сборки

Основа: текущий прототип `money.log` (vanilla JS без сборки, localStorage, `node --test`).
Цель: бизнес-логика из ТЗ — «Пришло / Ушло / Перевёл / Долги», где одна операция вводится один раз,
а счета, категории, бюджеты, резервы и прогноз пересчитываются сами.

## 1. Ключевые решения

1. **Стек не меняем.** Чистый JS, без фреймворков и сборки, стиль init.Habits сохраняем.
   Логика — в чистых модулях `dist/core/*.js` (работают и в браузере, и в node-тестах), UI — отдельно.
2. **Журнал — единственный источник правды.** Хранятся только события (операции, планы, правила).
   Остатки, бюджеты, резервы, прогноз, аналитика — всегда *вычисляются* из журнала, никогда не хранятся.
   Отсюда бесплатно получаем п.10 ТЗ: исправил сумму → всё пересчиталось.
3. **Две независимые «оси» у операции:**
   - **проводки (legs)** — что произошло с деньгами на счетах: `{accountId, amountCents}` со знаком;
   - **разнесение (allocations / позиции чека)** — на что потрачено: `{categoryId, amountCents, item?, qty?}`.
   Позиции чека живут только в разнесении и **никогда не трогают баланс** — двойного списания нет по построению.
4. **Счёт — универсальная сущность** с видом: `debit | cash | savings | credit_card | loan | person`.
   Кредит — это счёт с отрицательным остатком; «одолжил Пете» — счёт-требование вида `person`.
   Так долги, переводы и возвраты не требуют особой математики.
5. **План ≠ факт.** Ожидаемые операции (`planned`) не влияют на остаток, пока пользователь не подтвердит;
   подтверждение создаёт настоящую операцию со ссылкой на план и фиксирует отклонение суммы.
6. **iPhone — через PWA.** Приложение лежит на бесплатном HTTPS-хостинге (GitHub Pages / Cloudflare Pages),
   на iPhone ставится через Safari → «Поделиться» → «На экран „Домой“». Нужны manifest, иконки,
   service worker для работы офлайн и вёрстка под мобильный экран (этап 0). Нативное приложение не делаем.
7. **Деньги — целые копейки** (как сейчас), даты — `YYYY-MM-DD`.
8. **Хранилище:** пока localStorage + JSON-копия; схема v2 с миграцией из v1
   (все старые записи → счёт «Основной», начальный остаток → стартовый остаток счёта).

## 2. Модель данных (схема v2)

```
accounts:     id, name, kind, openingCents, openingDate, archived
categories:   id, name, parentId|null, kind: expense|income
merchants:    id, name, lastCategoryId               (память подсказок, можно и вычислять)
operations:   id, type, date, note, merchantId?, counterparty?,
              legs[], allocations[], links{refundOf?, reimburses?, plannedId?},
              deleted, revisions[]                    (история правок)
schedules:    id, template (как operation), rule {freq, day}, startDate, endDate?
reserves:     id, accountId, amountCents, dueDate, label, scheduleId?, releasedBy?
budgets:      id, categoryId, period: month, limitCents
loans:        accountId, rateYearly, termMonths, paymentDay, method: annuity|diff
```

Типы операций и их проводки:

| type            | legs                                          | allocations            |
|-----------------|-----------------------------------------------|------------------------|
| income          | +счёт                                         | источник дохода        |
| expense         | −счёт                                         | категории / позиции    |
| transfer        | −откуда, +куда (сумма легов = 0)              | — (комиссия = expense) |
| loan_payment    | −счёт, +loan(основной долг)                   | проценты, комиссии     |
| refund          | +счёт, ссылка на исходную покупку             | −категории исходной    |
| reimbursement   | +счёт, ссылка на общую покупку                | −доля в категории      |
| lend / borrow   | −счёт, +person (или наоборот)                 | —                      |
| adjustment      | ±счёт (сверка с банком, с пояснением)         | «Корректировка»        |

Инвариант: для `expense` сумма allocations = сумма списания; при несовпадении чека UI предлагает
строку «скидка / доставка / ошибка».

## 3. Вычисляемые представления (чистые функции)

- `balances(journal, date)` — остатки по счетам; «мои деньги» = сумма без loan/person.
- `spending(journal, period, filter)` — по категориям, магазинам, позициям.
- `budgetStatus(journal, month)` — потрачено / осталось / темп и прогноз до конца месяца.
- `occurrences(schedules, from, to)` — развёртка регулярных правил минус подтверждённые.
- `freeBalance(journal, date)` — остаток − активные резервы; резерв «гаснет» при оплате связанного плана.
- `forecast(journal, untilDate)` — день за днём до след. зарплаты, дата первого дефицита.
- `loanSplit(loan, balance, date, amount)` — основной долг / проценты; пересчёт графика после досрочки.
- `suggest(journal, merchant)` — последняя категория, частые позиции, последние цены, частый счёт.

## 4. Этапы

Каждый этап = отдельная ветка/коммит, рабочее приложение и зелёные тесты в конце.

| # | Этап | Что пользователь получает |
|---|------|---------------------------|

| 1 | Счета + перевод + сверка остатка | Сбер / Т-Банк / наличные, «Перевёл», корректировка на 200 ₽ |
| 2 | Категории (2 уровня) + быстрый расход + память магазинов | «− Ушло» за несколько секунд, подсказки по «Пятёрочке» |
| 3 | Подробный чек | Позиции, кол-во, проверка суммы, разнесение по категориям |

## 5. Как распределяем модели (экономия)

| Кто | Что делает |
|-----|------------|
| **Opus** (основная сессия) | Этот план, точная спецификация каждого этапа (функции, сигнатуры, тест-кейсы из ТЗ), код-ревью диффа, решения при спорных местах |
| **Sonnet** (субагент) | Реализация логики этапа в `core/*` строго по спецификации + тесты; UI-формы этапа |
| **Haiku** (субагент) | Механика: тестовые фикстуры, перенос текстов, README, мелкие правки вёрстки, миграционные тесты |

Цикл одного этапа:
1. Opus пишет `docs/specs/stage-N.md` (короткий, с готовыми тест-кейсами).
2. Sonnet пишет код + тесты, гоняет `npm test` до зелёного.
3. Haiku доделывает механическое (тексты, README).
4. Opus смотрит дифф, запускает приложение в браузере, коммит.

Тяжёлые участки, которые лучше не отдавать дешёвым моделям целиком: модель проводок (этап 0),
прогноз/резервы (4–5) и кредитная математика (7) — там спецификацию с примерами пишет Opus, а
Sonnet только реализует.
