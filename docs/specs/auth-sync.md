## Принципы
1. **Работает без регистрации.** Аккаунт — опция: «сохранять копию в облаке и синхронизировать устройства».
   Как сейчас, всё хранится на устройстве; вход ничего не ломает и не обязателен.
2. **Сервер не видит деньги.** Журнал шифруется на устройстве (сквозное шифрование, E2E). На сервере — только
   зашифрованные записи, email и служебные метки времени. Утечка базы ≠ утечка финансов.
3. **Без паролей, где можно.** Основной вход — passkey (Face ID / Touch ID, хранится в iCloud Keychain и работает
   на iPhone и Mac). Запасной — код на email.
4. **Всё на том же Cloudflare Worker**, что раздаёт приложение: один адрес, cookie без CORS, бесплатный тариф.

## Архитектура
```
iPhone / Mac (PWA)                        Cloudflare Worker  (finance-log)
 ├─ журнал в localStorage/IndexedDB        ├─ статические файлы (как сейчас)
 ├─ ключ данных DK (256 бит, случайный)    ├─ /api/auth/*   passkey + email-код, сессии
 ├─ шифрование записей AES-GCM(DK)  ─────▶ ├─ /api/sync/*   зашифрованные записи
 └─ DK «завёрнут» (wrapped):               └─ D1 (SQLite): users, credentials, sessions,
     • passkey PRF  (iOS 18+)                               records, wrapped_keys
     • код восстановления (24 символа)
```

### Вход
- **Регистрация**: email → код из письма (6 цифр, 10 минут, 5 попыток) → создать passkey на этом устройстве →
  показать **код восстановления** один раз («сохраните в заметки/менеджер паролей»).
- **Вход на новом устройстве**: passkey (если iCloud Keychain синхронизирован — Face ID и всё) или email-код
  + код восстановления (нужен, чтобы расшифровать данные).
- Сессия: cookie `HttpOnly; Secure; SameSite=Lax`, 30 дней, продлевается при использовании; список устройств и
  «выйти везде» в настройках.
- Защита: лимит попыток по IP и email (Durable Object или D1-счётчик), заголовок `X-Requested-With` против CSRF.
- Письма: Cloudflare Email Sending или Resend (3 000 писем/мес бесплатно). Доставляемость на mail.ru/yandex — проверить.

### Шифрование
- DK генерируется на первом устройстве; каждая запись (операция, счёт, категория, настройки) шифруется отдельно:
  `{id, kind, updatedAt, deleted, iv, ciphertext}` — сервер видит только id и время.
- DK хранится на сервере только в обёрнутом виде: `wrap(DK, PRF-ключ passkey)` и `wrap(DK, ключ из кода восстановления через PBKDF2/Argon2)`.
- Потеря всех устройств **и** кода восстановления = данные не восстановить (честно предупреждаем при регистрации).

### Синхронизация
- Модель «запись = операция» уже есть (id, updatedAt, deleted, revisions) — идеально для синка.
- `POST /api/sync {since: cursor, changes: [...]}` → сервер сохраняет, возвращает изменения других устройств после cursor и новый cursor.
- Конфликт (одна запись правилась на двух устройствах офлайн): побеждает более поздний `updatedAt`, проигравшая
  версия кладётся в `revisions` — ничего не теряется, видно в истории правок.
- Удаления — флаг `deleted` (как сейчас), физически не удаляем.
- Синк: при запуске, после каждой записи (с задержкой 2 с), при возврате во вкладку; офлайн — очередь.

## Этапы
- **A. Аккаунт**: email-код + passkey, сессии, экран «аккаунт» в настройках, выход. (Данные ещё не синкаются.)
- **B. Облачная копия**: шифрование, загрузка/восстановление всей базы одной кнопкой (замена ручной «скачать копию»).
- **C. Синхронизация устройств**: инкрементальный синк по записям, индикатор `[sync ok]` в топбаре.
- **D. (потом)** Общий бюджет на двоих — отдельный общий ключ для выбранных счетов.

## Риски и вопросы
- **Доступность Cloudflare из России** — если начнутся перебои, API можно перенести на VPS (тот же код на Hono/Node + SQLite).
- **152-ФЗ**: если сервисом будут пользоваться другие люди из РФ, email — персональные данные, формально требуется
  их хранение в РФ. Для личного использования/друзей — не критично; для публичного сервиса — нужен сервер в РФ.
- **PRF у passkey** работает в Safari iOS 18+/macOS 15+; на старых устройствах — вход по коду восстановления.
